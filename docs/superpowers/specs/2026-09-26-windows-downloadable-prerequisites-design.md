# Windows downloadable prerequisites and branded setup — v0.5 design

Status: design for review. This document describes the approved user-facing behavior; it does not claim that a WiX bundle has been built or installed successfully.

## Intent and scope

The Beskid Windows setup EXE must leave a clean x64 Windows 10-or-later machine able to run the installed CLI and JIT tests. It must offer an unchecked **Install developer tools** choice that additionally downloads and installs the tools needed by `beskid build` and `beskid run`: MSVC x64 Build Tools, Windows SDK libraries, and LLVM's `lld-link`. No copy of `lld-link` or those developer installers is embedded in the Beskid setup EXE. The setup UI, executable icon, MSI dialogs, and installed-product entries must use the existing Beskid logo. The standalone MSI remains available and fails with an actionable VC++ prerequisite message when necessary.

This is an installer and native-toolchain integration change, not a change to the Beskid language standard. Release work is split between `beskid_distrib` (downloadable setup and branding) and `beskid_compiler` (discovering an installed Windows native toolchain). Both parts are required for the end-to-end developer-tools claim.

## Selected approach and alternatives

Use one WiX v4 Burn setup EXE with a custom theme for the stock WixStandardBootstrapperApplication (WixStdBA). A checkbox bound to a numeric Burn variable controls the optional package chain. This retains WiX's detection, download, hash verification, caching, reboot, and logging behavior without writing a custom bootstrapper application. The default variable value is `0`; unattended installation also defaults to runtime-only, and an explicit documented command-line variable selects developer tools.

A separate developer-tools EXE would avoid a custom theme but make the requested choice a second installer. A custom bootstrapper application would provide more UI control but add a new native program to ship and maintain. Neither is selected for v0.5. WiX documents [custom WixStdBA themes](https://docs.firegiant.com/wix/tools/burn/wixstdba/), [checkbox-to-variable binding](https://docs.firegiant.com/wix/schema/thmutil/checkbox/), and [conditional EXE packages](https://docs.firegiant.com/wix/schema/wxs/exepackage/). Their composition is a design inference and must be proven by a real WiX build and install test.

## Package chain and provenance

Burn runs the packages in this order: VC++ x64 Redistributable when absent or below 14.40; if selected, Visual Studio 2022 Build Tools with the C++ workload, x64/x86 MSVC tools, and a supported Windows SDK; if selected, the official LLVM Windows x64 installer; then the Beskid MSI. All three vendor EXE payloads are downloaded by Burn on the user's machine rather than embedded. The Visual Studio bootstrapper itself downloads the selected workload components from Microsoft. Its invocation uses `--quiet --wait --norestart` and explicit component IDs, because Microsoft lists the MSVC tools and SDK as recommended rather than required parts of `Microsoft.VisualStudio.Workload.VCTools` ([command-line contract](https://learn.microsoft.com/en-us/visualstudio/install/use-command-line-parameters-to-install-visual-studio?view=vs-2022), [component catalog](https://learn.microsoft.com/en-us/visualstudio/install/workload-component-id-vs-build-tools?view=vs-2022)). The official [LLVM Windows release](https://github.com/llvm/llvm-project/releases) supplies the installer containing `lld-link`; its unattended arguments and installed-file location must be verified against the selected release before publishing.

A checked-in prerequisite lock records, for each vendor bootstrapper or installer, its vendor, product/version, immutable official HTTPS URL, SHA-512 digest, byte size, and license/source link. Packaging fails if any field is absent or if a fetched release-audit copy differs. WiX `ExePackagePayload` uses the locked `Name`, `DownloadUrl`, `Hash`, and `Size`; [WiX's remote-payload schema](https://docs.firegiant.com/wix/schema/wxs/exepackagepayload/) requires these fields together. A moving `aka.ms` permalink alone is not a release pin. The package build verifies the locked vendor bytes and signatures where the vendor publishes them, then does not include those bytes in the setup EXE. A new vendor version is a reviewed lockfile update, not a silent installation-time substitution.

The VC++ package is mandatory and retained when Beskid is removed. Developer tools are installed only when selected, are also retained on Beskid uninstall, and must not be removed when a user later deselects the option during repair or modify. Each prerequisite is vital: download, hash, installation, or post-install validation failure stops the setup before the Beskid MSI is installed. An offline clean machine receives a clear network/prerequisite failure; no unverified fallback is allowed. Vendor installers may require elevation and a reboot; Burn reports a pending reboot rather than restarting without the user's choice. Logs name the failed vendor package and point to the vendor/Bundle log. The UI links to Beskid and third-party license terms before the optional download begins.

## Beskid branding

`assets/icons/beskid-512.png` remains the single raster source, with `assets/icons/beskid-logo.svg` as its source artwork. The packaging pipeline derives a multi-size ICO and MSI banner/dialog art reproducibly, then validates the generated files before invoking WiX. The generated ICO is used by `Bundle/@IconSourceFile` for the setup EXE and bundle Add/Remove Programs entry, and by the MSI `Icon`/`ARPPRODUCTICON` pair. WixStdBA's `LogoFile` displays the Beskid mark in the custom welcome/options/progress/completion theme; the theme keeps the opt-in label and a large-download warning legible at normal Windows scaling. The standalone MSI uses `WixUIBannerBmp` and `WixUIDialogBmp` overrides so its directory-picker flow is branded too. These are distinct WiX surfaces: [bundle icon](https://docs.firegiant.com/wix/schema/wxs/bundle/), [WixStdBA logo/theme](https://docs.firegiant.com/wix/schema/bal/wixstandardbootstrapperapplication/), and [MSI dialog artwork](https://docs.firegiant.com/wix/tools/wixext/wixui/). Existing logo/ARP authoring is retained and extended, not replaced by generic WiX graphics.

## Native-toolchain use after installation

The setup choice is only successful when `beskid build` and `beskid run` work from an ordinary new shell, not only from a preconfigured x64 Native Tools prompt. The compiler locates a complete VS 2022 instance using Microsoft's installed-instance tooling, obtains the x64 `PATH`, `INCLUDE`, `LIB`, and SDK environment through the vendor's developer-command script, and passes that environment only to child native-tool processes. Explicit user-provided toolchain environment remains authoritative. The compiler checks for `cl`, a linker, and required import libraries and reports an actionable error when the installation is incomplete; it must not alter the user's global environment. The installer validates the selected tools after vendor setup, including an executable `lld-link`. Microsoft documents [VS instance discovery](https://learn.microsoft.com/en-us/visualstudio/extensibility/locating-visual-studio?view=visualstudio); Beskid's current `cl`/linker `PATH` dependence is recorded in the adjacent [research note](../../research/2026-09-26-windows-downloadable-prerequisites.md).

## Verification and release gate

Static contract tests check the default-off variable, package order, remote-payload pins, mandatory VC++ floor, permanent prerequisite behavior, branded assets, and that no developer installer or `lld-link` binary is embedded. A real WiX v4 build must produce both MSI and setup EXE; inspect the bundle manifest and EXE resources, not only mocked `wix` calls. On disposable Windows VMs, test default runtime-only install, selected developer-tools install, preexisting prerequisites, download/hash failure, offline failure, repair/modify deselection, upgrade, and uninstall. Test `beskid test`, `beskid build`, and `beskid run` from a fresh ordinary shell after selected setup, and visually inspect the welcome, options, progress, success/failure, and MSI directory-picker screens at 100% and 150% scaling. Record installed component versions, logo screenshots, hashes, and logs. Do not call the snippets or installer working until these gates pass.

No push, merge to `main`, publication, credential change, or change to an external service is part of this design approval.
